# 실시간 채팅 신뢰성 개선

SnapBook은 네일샵의 예약과 상담을 실시간 채팅으로 처리합니다.  
재접속 복구 기능을 개발하면서 시작한 질문을 두 가지 잠재 장애 시나리오로 확장해 실제 애플리케이션 환경에서 검증했습니다.


## 핵심 결과

| 문제 | 개선 결과 |
|---|---:|
| 다른 방의 느린 연결이 정상 채팅까지 지연 | p95 **915→255ms**, 최대 **3,436→1,427ms** |
| 배포 후 모든 클라이언트가 동시에 재접속 | 실패 재시도 **122→28회**, 피크 재접속 **28→9명/초** |

---

## 1. 느린 연결도 안전한가?

### 문제를 발견한 흐름

재접속 후 누락 메시지를 복구하는 기능을 만들면서 다음 의문이 생겼습니다.

> 연결이 완전히 끊어지지 않고 느리게 유지되면 서버는 어떻게 동작할까?

Spring 설정과 프레임워크 코드를 추적한 결과, 모든 채팅방의 서버→클라이언트 전송이 하나의 `clientOutboundChannel` 스레드풀을 공유한다는 사실을 확인했습니다.

느린 연결이 전송 스레드를 오래 점유하면 다른 채팅방의 메시지도 공용 큐에서 기다릴 수 있다고 판단했습니다.

### 가설을 검증한 과정

정상 채팅방의 수신 지연을 측정하면서 다른 방에 느린 구독자 24명을 연결했습니다.

처음에는 문제가 재현되지 않았습니다.

1. 첫 번째 실험에서는 32KB 메시지가 테스트 클라이언트의 8KB 버퍼를 초과해 연결이 먼저 종료됐습니다.
2. 버퍼를 수정한 뒤에는 완전히 멈춘 연결이 Spring의 512KB 보호 한도로 빠르게 종료됐습니다.
3. 이후 데이터를 조금씩 읽는 `trickling consumer`로 조건을 바꾸자 문제가 재현됐습니다.

| 지표 | 기준선 | 느린 연결 24개 |
|---|---:|---:|
| p95 지연 | 3ms | **915ms** |
| 최대 지연 | 4ms | **3,436ms** |
| 느린 세션 생존 | - | **24/24** |

완전히 죽은 연결은 기존 보호 장치가 처리했지만, 조금씩 읽는 연결은 종료 조건을 피하면서 공용 스레드를 계속 점유했습니다.

### 결정과 결과

세션 하나가 공용 전송 자원을 오래 점유하지 못하도록 전송 한도를 명시했습니다.

```java
registry.setSendTimeLimit(1_000)
        .setSendBufferSizeLimit(128 * 1024);
```

재접속 후 최신 메시지를 다시 조회하는 복구 경로가 있었기 때문에, 느린 연결을 빠르게 종료하더라도 최근 누락 메시지를 복구할 수 있었습니다.

| 지표 | 변경 전 | 변경 후 |
|---|---:|---:|
| p95 지연 | 915ms | **255ms** |
| 최대 지연 | 3,436ms | **1,427ms** |
| 후반부 지연 누적 | 지속 | **제거** |

이 변경은 공유 스레드풀 구조를 없앤 것이 아니라, 끝없이 누적되던 지연을 빠른 연결 종료와 회복으로 바꾼 것입니다.

## 2. 모두 동시에 재접속하면?

### 다음 질문

첫 번째 사례에서는 느린 연결을 종료하고 재접속으로 복구하도록 했습니다. 여기서 다시 질문을 확장했습니다.

> 개별 연결을 끊는 것은 안전하지만, 배포로 모든 연결이 동시에 끊기면 어떻게 될까?

배포 스크립트를 확인하니 기존 컨테이너를 `docker rm -f`로 제거하고 있었습니다. JVM이 정리 작업을 수행할 수 없는 SIGKILL 경로였습니다.

모든 클라이언트가 종료 이유 없이 동시에 끊기고, 같은 간격으로 재접속하면서 서버가 살아나는 순간 요청이 집중될 것이라고 가정했습니다.

### 실제 배포로 검증

실제 Docker 이미지에 WebSocket 클라이언트 30개를 연결하고 기존 배포 명령으로 컨테이너를 교체했습니다.

| 변경 전 측정 | 결과 |
|---|---:|
| 동시 비정상 종료 | 30명 |
| 다운타임 중 실패 재시도 | **122회** |
| 서버 재기동 직후 재접속 | **28명/초** |
| 동시에 실행된 메시지 재조회 | **28건/초** |

재접속 기능은 개별 장애에서는 복구 수단이었지만, 모든 클라이언트가 동시에 실행하면 콜드 서버를 공격하는 부하 증폭기가 됐습니다.

### 결정과 결과

종료와 재접속 경로를 함께 변경했습니다.

- 배포: `docker rm -f` → `docker stop --time 30`
- 서버: Spring graceful shutdown 적용 및 `server-restart` 종료 사유 전달
- 재접속: 즉시 재시도 대신 지터와 지수 백오프로 시간 분산

종료 순서를 명시하기 위해 웹소켓 세션 정리를 별도 단계로 분리했습니다. `SmartLifecycle`의 `stop()`은 phase가 큰 것부터 실행되므로, 웹서버가 HTTP 요청을 드레인하기 전에 세션을 먼저 닫습니다.

```java
@Component
public class WebSocketShutdownDrain implements SmartLifecycle {

    static final CloseStatus SERVICE_RESTART = new CloseStatus(1012, "server-restart");

    @Override
    public void stop() {                       // 1. 세션에 종료 사유 전달
        sessionRegistry.closeAll(SERVICE_RESTART);
    }                                          // 2. 이후 graceful shutdown이 HTTP 드레인

    @Override
    public int getPhase() {
        return Integer.MAX_VALUE;               // 종료 시 가장 먼저 실행
    }
}
```

전송 계층에서 세션을 추적해야 종료 시점에 한 번에 닫을 수 있으므로, 기존 전송 설정 지점에 데코레이터를 붙였습니다.

```java
registry.setSendTimeLimit(1_000)
        .setSendBufferSizeLimit(128 * 1024)
        .addDecoratorFactory(handler -> new WebSocketHandlerDecorator(handler) {
            @Override
            public void afterConnectionEstablished(WebSocketSession session) throws Exception {
                sessionRegistry.add(session);
                super.afterConnectionEstablished(session);
            }
            ...
        });
```

| 지표 | 변경 전 | 변경 후 |
|---|---:|---:|
| 실패 재시도 | 122회 | **28회** |
| 피크 재접속 | 28명/초 | **9명/초** |
| 재조회 응답 p50 | 139ms | **9ms** |

다만 지터·백오프는 재현 클라이언트에서 효과를 검증한 단계이며 실제 프론트엔드 반영은 별도 작업입니다. 단일 컨테이너 교체로 인한 약 4초의 다운타임도 남아 있습니다.
