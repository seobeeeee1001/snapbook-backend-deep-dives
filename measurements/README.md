# 가공하지 않은 측정 원본

문서에 적은 수치를 **직접 검산하실 수 있도록** 원본 로그를 그대로 두었습니다.

```bash
python3 aggregate.py before   # 개선 전 (docker rm -f + 즉시 재시도)
python3 aggregate.py after    # 개선 후 (docker stop + graceful + 지터)
```

실행 결과:


## 파일 설명

| 파일 | 내용 |
|---|---|
| `storm_{before,after}.log` | 클라이언트 하니스 원본 출력. `EVT\|epochMs\|clientId\|event\|detail` 형식 |
| `probe_{before,after}.log` | HTTP 가용성 프로버. 50ms 간격 `epochMs\|결과` |
| `tkill_{before,after}.txt` | 배포 명령을 실행한 시각(epoch ms). 모든 상대 시각 `T+`의 기준점 |
| `shutdown_evidence.txt` | graceful 종료가 실제로 실행됐다는 서버 로그 |
| `aggregate.py` | 위 로그에서 지표를 계산하는 스크립트 (문서의 모든 수치가 여기서 나옵니다) |

## 집계를 하니스와 분리한 이유

하니스는 **사건만 기록**하고 집계는 하지 않습니다(`EVT|...` 한 줄씩 stdout). 그래서:

- 나중에 다른 방식으로 다시 집계할 수 있습니다 (예: p99 추가, 클라이언트별 분포)
- 집계 로직에 버그가 있어도 **원본 관측값은 손상되지 않습니다**
- 제3자가 같은 로그로 다른 결론을 검증할 수 있습니다

## 읽을 때 주의

- 개발 머신 로컬 도커 기준입니다. 부팅 시간(4~5초)은 EC2에서 더 길고, 루프백은 실제 모바일 네트워크보다 버퍼가 관대합니다. **측정값은 하한으로 읽어야 합니다.**
- `shutdown_evidence.txt`의 "세션 31개"는 클라이언트 30개 + 종료 코드 관측자 1개입니다.
- 개선 후에도 다운타임 창이 남아 있는 것은 실패가 아니라 **예상된 결과**입니다. 단일 컨테이너 교체 구조의 한계이고, 이 개선의 목표는 절단 품질과 재접속 폭풍이었습니다.
